### Step 1 — Confirm the eval dataset
Call `signal_phase` this response with the step for the phase you are in — this phase: `step-1-dataset`.

The eval dataset needs a `messages` column. The trailing assistant
message is used as the reference answer.

**For a tuned model, FIRST offer reusing an existing eval set — do not
jump to generating a fresh one.** Scoring a model on a set another model
was already scored on is what makes the numbers line up in the Evaluation
tab, so reuse is the preferred path. Call `list_reusable_eval_sets` with
the training job ID. Each returned set is flagged `recipe_match: true`
when it was generated by the SAME SDG recipe (teacher + assessor prompt)
as this model's training data — those are the fair, same-task sets.
Present the recipe-matching sets (already ordered, newest first) as
options, each labeled with its name and the sibling models already scored
on it — e.g. "Reuse <name> — already scored: <models>; comparable in the
Evaluation tab". When the user picks one, pass its `eval_data_run_id` as
`eval_data_run_id` and go straight to Step 1.5 (`step-1_5-how-much`) (skip
the split / generation paths). Whenever the user declines reuse — whether
they want a brand-new held-out set, an uploaded or split dataset, or any
other source — or `recipe_match_available` is false (no same-task set
exists yet), fall through to the suggestions below. (If
`training_recipe_known` is false the model was not trained from an SDG job,
so nothing can be recipe-matched; you may still offer the listed sets, but
note they are not verified same-task.)

**Otherwise, use the training dataset as the trail to a held-out set.**
Call `get_job` on the training job, read its `data_run_id` (a dataset
run) or parent SDG job, then find the natural hold-out:

- Call `get_dataset` on the training dataset. If its `source` is
  `"split"`, use the originating split job's `split_run_id` and
  `complement_run_id` to identify the sibling hold-out — the one the
  model was NOT trained on. `source_run_id` alone is not a unique
  split-job identifier (the same source can have several split jobs, so
  matching on it can pick a sibling from a different split). If the
  originating job or sibling ID is unavailable, do not auto-select a
  dataset from `list_datasets`; ask the user or create a fresh hold-out
  instead. When resolved, suggest the sibling as the default: same
  distribution, zero leakage.
- Otherwise (the model was trained on the whole dataset), suggest a
  fresh hold-out split of the training dataset (`split_dataset`, e.g.
  fraction 0.2, strategy random) — matched distribution, but it shares
  records with the training data, so mention the leakage trade-off.

Always present the suggestion as a choice — the user may want a
different dataset. The other ways to supply an eval dataset, for any
model (tuned or not):

- **A completed SDG job** generated separately from the training data
  (best isolation, no leakage) — use its job ID as `parent_job_id`.
- **An uploaded dataset** from the Datasets page — use its MLflow run
  ID as `eval_data_run_id`.
- **A split of an existing dataset** — `split_dataset` on its run ID
  (fraction 0.2, strategy random). The job materializes the portion
  AND its complement; use the finished job's `config.split_run_id` as
  `eval_data_run_id` (mention the leakage trade-off if the complement
  is, or overlaps, the training set).

If none of these exist, a held-out eval set must be generated with an SDG
job — you don't do this yourself; hand back to the orchestrator via
`request_orchestrator_help` (see the `held-out-eval-set` phase). CALL the
tool — do NOT narrate handing off in prose. It runs SDG and resumes you
with the new SDG job ID as `parent_job_id`; resume at Step 1.5
(`step-1_5-how-much`) to confirm how much of the fresh set to score (a
held-out request doesn't say how much to use), then continue to Step 3
(`step-3-metrics`) — unless the user already fixed the amount.
